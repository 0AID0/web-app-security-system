Что такое RLS?

Row-Level Security (RLS) - это функция PostgreSQL, которая позволяет ограничивать доступ к строкам таблицы на основе политик безопасности. Каждый пользователь видит только те данные, к которым у него есть доступ.

Пример простой политики:

Пользователи могут видеть только свои документы
CREATE POLICY user_policy ON documents
  FOR SELECT TO standard_user
  USING (owner_id = current_user_id());
Пояснение:
Эта политика разрешает пользователям с ролью 'standard_user' видеть только те строки в таблице 'documents', где значение столбца 'owner_id' совпадает с ID текущего пользователя (возвращаемым функцией current_user_id()).

Основные преимущества:

  • Точный контроль доступа к данным на уровне строк
  • Прозрачность для приложения - не требует изменений в коде
  • Централизованное управление политиками в БД
  • Совместимость с существующими приложениями
  • Поддержка всех основных операций (SELECT, INSERT, UPDATE, DELETE)

Как работает RLS?

RLS использует политики безопасности, которые определяют какие строки могут быть видны или изменены конкретным пользователем. Политики применяются автоматически ко всех запросам.

Политика для менеджеров:

Менеджеры могут видеть документы своего отдела
CREATE POLICY manager_policy ON documents
  FOR ALL TO manager
  USING (department = current_department());
Пояснение:
Эта политика разрешает пользователям с ролью 'manager' выполнять любые операции (SELECT, INSERT, UPDATE, DELETE) только с теми документами, где значение столбца 'department' совпадает с отделом текущего пользователя.

Типы политик:

  • SELECT - контроль чтения данных
  • INSERT - контроль добавления данных (WITH CHECK)
  • UPDATE - контроль изменения данных (USING и WITH CHECK)
  • DELETE - контроль удаления данных
  • ALL - все операции

Примеры реализации

1. Базовые политики доступа

Политика для администраторов

Администраторы имеют полный доступ ко всем данным
CREATE POLICY admin_all_access ON documents
  FOR ALL TO admin
  USING (true) WITH CHECK (true);
Пояснение:
Эта политика дает полный доступ администраторам ко всем строкам таблицы 'documents'.
USING (true) - разрешает доступ к любым строкам при чтении.
WITH CHECK (true) - разрешает любые изменения (вставку, обновление).

Политика для обычных пользователей

Пользователи могут видеть и редактировать только свои документы
CREATE POLICY user_policy ON documents
  FOR ALL TO standard_user
  USING (owner_id = current_user_id())
  WITH CHECK (owner_id = current_user_id());
Пояснение:
Эта политика ограничивает доступ пользователей с ролью 'standard_user' только их собственными документами.
USING - определяет какие строки можно читать (SELECT).
WITH CHECK - определяет какие строки можно изменять (INSERT, UPDATE).
Оба условия проверяют, что owner_id документа совпадает с ID текущего пользователя.

Политика для публичных документов

Все пользователи могут видеть публичные документы
CREATE POLICY public_read_policy ON documents
  FOR SELECT TO public
  USING (is_public = true);
Пояснение:
Эта политика разрешает всем пользователям (роль 'public') читать документы, где is_public = true.
Обратите внимание, что эта политика не дает прав на изменение (INSERT, UPDATE, DELETE) публичных документов.

2. Расширенные сценарии

Политика для менеджеров отделов

Менеджеры могут видеть документы своего отдела и редактировать только определенные поля
CREATE POLICY manager_select_policy ON documents
  FOR SELECT TO manager
  USING (department = current_department());

CREATE POLICY manager_update_policy ON documents
  FOR UPDATE TO manager
  USING (department = current_department())
  WITH CHECK (
    department = current_department() AND
    title IS NOT NULL AND
    content IS NOT NULL
  );
Пояснение:
Это две политики для менеджеров:
1. SELECT политика - разрешает читать документы своего отдела.
2. UPDATE политика - разрешает обновлять документы своего отдела, но с дополнительными проверками:
- нельзя изменить отдел документа
- title и content не могут быть NULL

Обратите внимание, что нет политики для DELETE, поэтому менеджеры не могут удалять документы.

Политика временного доступа

Доступ только к документам, созданным за последний месяц
CREATE POLICY recent_docs_policy ON documents
  FOR SELECT TO temporary_user
  USING (created_at > now() - interval '1 month');
Пояснение:
Эта политика ограничивает доступ временных пользователей (роль 'temporary_user') только документами,
созданными за последний месяц. Это полезно для ограниченного доступа контрактников или временных сотрудников.

Комбинированная политика

Пользователи могут видеть свои документы или документы своего отдела, если они публичные
CREATE POLICY combined_policy ON documents
  FOR SELECT TO employee
  USING (
    owner_id = current_user_id() OR
    (department = current_department() AND is_public = true)
  );
Пояснение:
Эта политика позволяет сотрудникам (роль 'employee') видеть:
1. Все свои документы (owner_id = current_user_id())
2. Документы своего отдела, если они помечены как публичные (is_public = true)

Это пример сложного условия USING, объединяющего несколько условий с помощью OR.

3. Аудит и мониторинг

Таблица аудита изменений

Создание таблицы для хранения истории изменений документов
CREATE TABLE document_audit (
  id SERIAL PRIMARY KEY,
  document_id INTEGER NOT NULL,
  action VARCHAR(10) NOT NULL,
  changed_by INTEGER NOT NULL,
  changed_at TIMESTAMP DEFAULT now(),
  old_data JSONB,
  new_data JSONB
);
Пояснение:
Эта таблица будет хранить историю всех изменений документов:
- document_id - ссылка на измененный документ
- action - тип операции (INSERT, UPDATE, DELETE)
- changed_by - кто внес изменения
- changed_at - когда внесены изменения
- old_data/new_data - данные до и после изменения в формате JSONB

JSONB позволяет гибко хранить данные любого документа без жесткой привязки к структуре таблицы documents.

Триггерная функция для аудита

Функция, которая записывает изменения в таблицу аудита
CREATE OR REPLACE FUNCTION log_document_changes()
RETURNS TRIGGER AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    INSERT INTO document_audit (document_id, action, changed_by, new_data)
    VALUES (NEW.id, 'INSERT', current_user_id(), to_jsonb(NEW));
  ELSIF TG_OP = 'UPDATE' THEN
    INSERT INTO document_audit (document_id, action, changed_by, old_data, new_data)
    VALUES (NEW.id, 'UPDATE', current_user_id(), to_jsonb(OLD), to_jsonb(NEW));
  ELSIF TG_OP = 'DELETE' THEN
    INSERT INTO document_audit (document_id, action, changed_by, old_data)
    VALUES (OLD.id, 'DELETE', current_user_id(), to_jsonb(OLD));
  END IF;
  RETURN NULL;
END;
$$ LANGUAGE plpgsql;
Пояснение:
Эта триггерная функция записывает в таблицу аудита информацию о каждом изменении:
1. Для INSERT - записывает новые данные (NEW) в new_data
2. Для UPDATE - записывает старые (OLD) и новые (NEW) данные
3. Для DELETE - записывает удаляемые данные (OLD) в old_data

Функция использует to_jsonb() для преобразования строки таблицы в JSONB формат.

Создание триггера

Привязка функции аудита к таблице документов
CREATE TRIGGER document_audit_trigger
  AFTER INSERT OR UPDATE OR DELETE ON documents
  FOR EACH ROW EXECUTE FUNCTION log_document_changes();
Пояснение:
Этот триггер вызывает функцию log_document_changes() после каждого изменения в таблице documents.
Триггер срабатывает для каждой измененной строки (FOR EACH ROW) после выполнения операции (AFTER).

Важно: триггеры AFTER выполняются после проверки всех ограничений и политик RLS.

Практическое применение

RLS особенно полезен в следующих сценариях:

Мультитенантные приложения

Разделение данных между клиентами в SaaS-решениях:

CREATE POLICY tenant_policy ON documents
FOR ALL USING (tenant_id = current_tenant_id());
Подробнее о мультитенантности
Мультитенантная архитектура:
В SaaS-приложениях данные разных клиентов хранятся в одной БД.
RLS позволяет изолировать данные клиентов без создания отдельных таблиц или БД для каждого.

Как это работает:
1. Каждая строка содержит tenant_id (идентификатор клиента)
2. Политика автоматически добавляет условие tenant_id = current_tenant_id() к каждому запросу
3. Функция current_tenant_id() определяет клиента по контексту (JWT токен, сессия и т.д.)

Персональные данные

Ограничение доступа к персональным данным:

CREATE POLICY personal_data_policy ON users
FOR SELECT USING (id = current_user_id());
GDPR и защита данных
Соответствие GDPR:
RLS помогает соответствовать требованиям GDPR, ограничивая доступ к персональным данным.

Примеры использования:
1. Пользователи видят только свои профили
2. Менеджеры видят только данные своих подчиненных
3. HR видят все данные, но только для сотрудников своей компании

Важно: RLS дополняет, но не заменяет другие меры защиты (шифрование, маскирование).

Иерархические структуры

Доступ к данным на основе организационной иерархии:

CREATE POLICY hierarchy_policy ON documents
FOR SELECT USING (
  department_id IN (
    SELECT department_id FROM user_departments
    WHERE user_id = current_user_id()
  )
);
Иерархический доступ
Сложные иерархии:
RLS может реализовать сложные схемы доступа на основе организационной структуры:

1. Руководители видят данные своих подразделений
2. Сотрудники видят данные своих коллег в том же отделе
3. Матричные структуры с доступом по нескольким критериям

Производительность:
Для сложных условий USING важно иметь индексы на полях, используемых в условиях.

Временной доступ

Ограничение доступа по времени:

CREATE POLICY temporal_policy ON documents
FOR SELECT USING (
  valid_from <= now() AND valid_to >= now()
);
Временные ограничения
Сценарии использования:
1. Ограничение доступа к документам по времени публикации
2. Временный доступ для аудиторов и проверяющих
3. Сезонные или рекламные акции

Особенности:
- Можно комбинировать временные ограничения с другими условиями
- Для работы с часовыми поясами используйте TIMESTAMP WITH TIME ZONE
- Для частых изменений временных интервалов рассмотрите материализованные представления

Ограничения и рекомендации

Ограничения RLS:

  • Не влияет на команды TRUNCATE, REFERENCES, EXECUTE
  • Не применяется к владельцу таблицы (по умолчанию)
  • Может влиять на производительность сложных запросов
  • Не заменяет другие механизмы безопасности
Обходные пути
Для TRUNCATE:
- Используйте DELETE с политиками
- Ограничьте права на TRUNCATE

Для владельца таблицы:
- Установите параметр row_security = on для владельца
- Используйте отдельную роль для администрирования

Для REFERENCES:
- Используйте триггеры для проверки ссылочной целостности
- Ограничьте права на создание внешних ключей

Рекомендации:

  • Используйте индексы для полей в условиях USING
  • Избегайте сложных условий в политиках
  • Тестируйте производительность с включенным RLS
  • Комбинируйте RLS с другими механизмами безопасности
Оптимизация
Советы по оптимизации:
1. Создавайте индексы для полей, используемых в USING
2. Используйте простые булевы условия
3. Избегайте вызовов функций в USING (или кэшируйте их)
4. Для сложных условий рассмотрите материализованные представления

Мониторинг:
Используйте EXPLAIN ANALYZE для проверки планов запросов с RLS.

Советы по производительности:

  • Для часто используемых политик создавайте специальные индексы
  • Используйте простые условия в политиках
  • Избегайте вызовов функций в условиях USING
  • Периодически пересматривайте и оптимизируйте политики
Пример индекса
Пример создания индекса для политики:
Если у вас политика:
CREATE POLICY user_policy ON documents USING (owner_id = current_user_id());

Создайте индекс:
CREATE INDEX idx_documents_owner_id ON documents(owner_id);

Для составных условий создавайте составные индексы.

Интерактивная демонстрация RLS

Роли пользователей:
- Администратор: полный доступ ко всем документам
- Пользователь: доступ только к своим документам
- Менеджер: доступ к документам своего отдела
- Аудитор: доступ только к публичным документам
Типы запросов:
- SELECT: чтение данных
- INSERT: добавление новых данных
- UPDATE: изменение существующих данных
- DELETE: удаление данных

RLS политики могут по-разному ограничивать разные типы операций.
Доступные документы:
В системе есть 5 тестовых документов с ID от 1 до 5.
Каждый документ имеет:
- Владельца (owner_id)
- Отдел (department)
- Статус (public/private)

Попробуйте разные ID чтобы увидеть как RLS ограничивает доступ.

SQL запрос:

SELECT * FROM documents WHERE id = 1;

Выберите параметры и выполните запрос

Легенда статусов
Статусы документов:
- Публичный: доступен всем пользователям
- Приватный: доступен только владельцу
- Отдела: доступен сотрудникам того же отдела

Цвета статусов соответствуют цветам в таблице.
